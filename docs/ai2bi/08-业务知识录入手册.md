# 业务知识录入手册

## 适用对象

本手册面向业务负责人、数据分析师、数据开发人员和 Agent/Skill 维护人员。目标是让新增知识变成可审核、可测试、可发布的资产，而不是散落在聊天提示词或个人笔记中。

## 录入前的原则

1. 未验证的业务假设不能写成强制规则。
2. 未确认指标口径不能直接进入 Skill 或 Prompt。
3. 数据源连接、密码、Token、用户权限条件不得写进资产正文。
4. 表、字段、指标、规则、SQL 模板、Agent 和 Skill 使用稳定引用，不只依赖中文名称。
5. 所有发布资产都要有负责人、版本、状态、变更原因和测试记录。
6. 对无法证明的因果关系、未来预测或敏感数据处理，必须标记为不支持或走专项审批。

## 新增一个业务域的流程

```text
定义业务域
  -> 同步数据源、表和字段
  -> 建立指标
  -> 建立业务规则
  -> 添加已验证 SQL 模板
  -> 编写 Skill
  -> 配置 Agent
  -> 编写测试
  -> 审核发布
```

任何一步不完整时，业务域可以保留在草稿状态，但不应进入生产路由。

## 第一步：定义业务域

使用 [domain.yaml](./templates/domain.yaml)。至少写清：

- 业务域编码和中文名称。
- 负责团队和业务/数据负责人。
- 包含什么、不包含什么。
- 常用术语与别名。
- 相关或容易混淆的业务域。
- 初期支持的分析能力。

示例：对公存款域包含对公客户余额、日均、期限和客户结构；不包含零售存款、理财和贷款。

## 第二步：同步表和字段，并补充语义

数据开发或管理员先完成数据源连接、表字段同步和执行白名单配置。业务同事在资产页补齐表字段语义。

### 表至少录入

- 数据源、schema、物理表名、中文说明和所属层级。
- 更新频率、数据时区、数据负责人。
- 是否允许用于生产分析。
- 上游来源与已知质量限制。

### 字段至少录入

- 物理字段名、类型、中文说明。
- 字段角色：指标、维度、过滤、分区、主键或辅助字段。
- 是否允许聚合、默认聚合方式和单位。
- 是否敏感、是否可查询/导出、脱敏要求。
- 枚举值或样例仅在符合数据权限时维护。

不要把“猜测字段含义”写进字段说明。字段来源不清时，应标为待确认并禁止 Agent 使用。

## 第三步：建立指标

使用 [metric.yaml](./templates/metric.yaml)。每个准备发布的指标必须有：

- 稳定指标编码、中文名称和别名。
- 完整业务定义。
- 可执行或可验证的计算公式。
- 统计粒度和时间语义。
- 单位、币种或格式。
- 允许维度和强制过滤条件。
- 来源表字段或已验证 SQL 模板。
- 正例、反例和测试预期。

常见错误：

- 只写“消费金额”，不说明成功授权、币种、是否排除 ATM、交易状态和统计期间。
- 把“余额”同时用于期末、日均和月均余额。
- 让不同业务域使用相同中文名称但不同公式。

## 第四步：建立业务规则

使用 [business-rule.yaml](./templates/business-rule.yaml)。规则适合记录：

- 指标必需过滤，例如只统计成功授权交易。
- 时间和分区要求。
- 跨域隔离和禁止表。
- 异常判断阈值及其适用条件。
- 不能做的输出，例如无证据因果归因。

规则必须给正例和反例。仅写“注意过滤条件”不能被系统稳定执行。

## 第五步：维护 SQL 模板

使用 [sql-template.yaml](./templates/sql-template.yaml)。SQL 模板必须是已验证、只读、参数化且可测试的查询。

- 明确 SQL 方言和数据源。
- 把时间、客群、维度等做成参数。
- 标记关联的指标、表字段和必需过滤。
- 不固化用户行权限和敏感字段授权逻辑。
- 每次模板变更都重新运行 SQL 和 Evidence 测试。

SQL 模板用于稳定常见场景，不能替代 Agent 根据用户问题生成的受控 SQL。

## 第六步：编写 Skill

使用 [skill.md](./templates/skill.md)。Skill 描述场景知识和过程，不是资产的唯一事实源。

Front Matter 必须包含：

- `skill_id`、名称、版本、所属业务域和 Agent。
- 触发词和不适用场景。
- 输入条件，例如必要指标、维度或最低数据量。
- 输出要求和允许分析类型。
- 引用的指标、规则、表字段和 SQL 模板。

正文写业务背景、推荐步骤、注意事项、正反例和用户可理解的输出要求。不要把表结构、指标口径和权限规则重复复制到正文；应链接到对应资产引用。

## 第七步：配置 Agent

使用 [agent.yaml](./templates/agent.yaml)。Agent 是生产运行边界，需要明确：

- 它服务的业务域和负责人。
- 可回答知识问题、可取数、可做哪些基础分析。
- 路由信号和不适用信号。
- 可用 Skill、指标、规则、表策略。
- 允许的分析模板和最大查询数。
- QA 硬拦截策略。
- 测试集和发布要求。

不要让一个 Agent 通过模糊描述“覆盖全部业务”。跨域分析应由共享资产和独立规则明确授权。

## 第八步：编写测试

使用 [analysis-test-case.json](./templates/analysis-test-case.json)。每个 Agent 最少维护：

1. 路由测试：问题命中正确 Agent 和 Skill。
2. SQL 测试：表、字段、分区、强制过滤和方言正确。
3. Evidence 测试：回答的数字和计算可回溯。

测试应包含反例，例如：

- 不应命中本 Agent 的问题。
- 缺少时间范围时应澄清。
- 不含强制过滤的 SQL 必须阻断。
- 没有比较周期时不得输出环比。

## 第九步：审核与发布

发布前完成 [asset-intake-checklist](./templates/asset-intake-checklist.md)：

- 负责人确认业务含义。
- 数据负责人确认表字段和数据新鲜度。
- 权限负责人确认敏感字段和行权限策略。
- 自动与人工测试通过。
- 版本、变更原因、影响范围和回滚方式已记录。

发布后修改必须创建新版本。旧版本应先弃用再归档，不能直接删除已被历史分析任务引用的资产。

## 常见问题

### 用户问题没有匹配指标怎么办？

先创建候选指标或知识问答说明，保持草稿状态；不要让模型根据字段名自行定义正式指标。

### 只有一条汇总数据，能做趋势分析吗？

不能。可以回答汇总，也可以按已确认的分析计划补充查询日、周或月粒度数据。

### 能否把用户偏好写进业务规则？

不能。用户个人偏好写入个人 Memory；全局指标、规则和术语必须走资产审核。

### 能否让 Skill 直接写 SQL？

可以引用已验证 SQL 模板或提供受控示例，但真实 SQL 仍须经过最终执行策略和权限校验。
