# 整体架构与运行链路

## 架构原则

AI2BI 应在现有 SQLBot 能力上演进，而不是以新的聊天壳替代原系统。目标架构要求每个阶段有明确输入、输出、权限边界和可审计记录。

```text
身份与权限层
  -> 语义资产层
  -> Agent 与 Skill 层
  -> 分析编排层
  -> Evidence 与审计层
  -> 前端工作台层
```

## 六层职责

| 层 | 职责 | 不能承担的职责 |
| --- | --- | --- |
| 身份与权限 | 当前用户、工作区、Agent 授权、数据源/表/字段/行策略、配额 | 由 LLM 决定能否访问数据 |
| 语义资产 | 业务域、表字段语义、指标、规则、模板、血缘、质量要求 | 保存用户一次查询的临时结果 |
| Agent 与 Skill | 业务域路由、能力边界、资产引用、场景知识、分析模板 | 绕过数据权限或直接授权 SQL |
| 分析编排 | 口径澄清、分析计划、SQL 生成、执行、补充查询、状态机 | 把业务解释当成事实计算 |
| Evidence 与审计 | 版本快照、SQL、结果摘要、计算事实、QA、审计 | 修改已发布资产定义 |
| 前端工作台 | 输入、澄清、进度、结果、证据、报告和治理页面 | 仅靠前端隐藏实现权限 |

## 核心运行对象

### AnalysisContract

AnalysisContract 是用户本次分析的口径确认结果，至少包括：

```json
{
  "question": "2026年7月对公存款余额情况怎么样",
  "agent_ref": "corp_deposit_agent@1.0.0",
  "metric_refs": ["corp_deposit.balance@1.0.0"],
  "time_range": {"start": "2026-07-01", "end": "2026-07-31", "grain": "day"},
  "population": "对公客户",
  "dimensions": ["day", "customer_segment"],
  "mandatory_filters": ["有效客户"],
  "analysis_mode": "careful",
  "status": "confirmed"
}
```

Contract 未确认且关键口径存在歧义时，系统不能执行 SQL。关键歧义包括指标同名但算法不同、时间范围缺失、客群范围缺失、币种缺失、是否包含某类交易或比较基准不明确。

### AnalysisPlan

AnalysisPlan 是 Agent 基于 Contract 制定的受控执行计划，不是模型自由调用工具的清单。

```json
{
  "task_id": "task_xxx",
  "queries": [
    {"id": "summary", "purpose": "获取期间汇总", "required": true},
    {"id": "trend", "purpose": "获取每日趋势", "required": false},
    {"id": "ranking", "purpose": "获取客户贡献排名", "required": false}
  ],
  "operators": ["summary", "trend", "ranking", "concentration"],
  "limits": {"max_queries": 3, "max_rows_per_query": 1000, "timeout_seconds": 60}
}
```

每一条计划查询都必须由同一权限上下文验证，并记录实际使用的表、字段、版本和结果摘要。

### EvidencePack 与 AnalysisFacts

EvidencePack 记录查询确实返回了什么；AnalysisFacts 记录后端基于结果做了哪些确定性计算。二者是分析 LLM 的唯一数据依据。

```text
EvidencePack = SQL + 权限范围 + 结果 + 指标上下文 + 来源数值
AnalysisFacts = SQL 直接事实 + 后端计算事实 + 公式 + 输入引用
```

最终回答不应直接从“用户问题 + 模型记忆”生成，而应从 EvidencePack 和 AnalysisFacts 生成。

## 目标运行链路

```text
用户提交问题
  -> 身份、工作区、数据源权限解析
  -> Agent 路由和 Agent 授权检查
  -> 问题分类：知识问答 / 直接查询 / 审慎分析 / 受控探索
  -> 加载已发布资产版本
  -> 形成或澄清 AnalysisContract
  -> 生成并校验 AnalysisPlan
  -> 逐条生成 SQL
  -> 最终执行策略校验
  -> SQL 执行与结果限制
  -> 构建 EvidencePack
  -> 运行确定性分析引擎，产出 AnalysisFacts
  -> 分析 LLM 根据事实生成解释
  -> QA：SQL、结果、证据、回答
  -> 保存 AnalysisTask 与审计记录
  -> SSE 返回进度、结果、证据和完成状态
```

## SQL 最终执行策略

以下顺序属于强制执行合同，任何 Prompt 或模型输出均不能替代：

```text
1. 解析当前用户、工作区、Agent、数据源和权限策略
2. 解析 SQL AST，限制为允许方言的只读语句
3. 校验表是否同时位于数据源白名单和 Agent 表策略中
4. 校验字段是否允许访问，拒绝敏感字段或应用脱敏表达式
5. 注入并验证行权限条件，不允许依赖 LLM 自行补写
6. 校验必需分区、业务强制过滤和 LIMIT/扫描限制
7. 执行并限制超时、返回行数和结果大小
8. 记录权限决策、SQL、参数和执行摘要
```

## 受控多查询规则

多查询是“基本分析”必要能力，但只能在 AnalysisPlan 内执行。

| 规则 | P0/P1 默认值 | 说明 |
| --- | --- | --- |
| 最大查询数 | 3 | 单次任务最多三条分析 SQL |
| 单条返回行数 | 1000 | 前端展示和 Evidence 使用不同摘要上限 |
| 总执行时长 | 60 秒 | 超时后停止未开始的可选查询 |
| SQL 失败处理 | 必需查询失败则任务失败；可选查询失败则降级 | 不能把失败查询当成零值 |
| 用户取消 | 支持 | 停止后续 SQL 和 LLM 调用，保留已完成审计 |
| 重试 | 默认 0 次 | 仅允许对网络类、幂等故障做受控重试 |
| 跨域数据 | 默认禁止 | 必须由已发布的共享资产和 Agent 规则显式允许 |

## 分析任务状态机

```text
created
  -> clarifying
  -> contract_confirmed
  -> planning
  -> querying
  -> analyzing
  -> qa_review
  -> completed

任意状态可进入：cancelled / blocked / failed / partially_completed
```

`blocked` 表示权限、口径、治理或 QA 硬规则不允许继续；`failed` 表示执行或系统错误；`partially_completed` 只允许在非关键可选分析查询失败且剩余结果仍有明确说明时使用。

## 现有模块映射

| 现有模块 | 可复用能力 | 目标改造方向 |
| --- | --- | --- |
| `backend/apps/chat/task/llm.py` | 聊天主链路、SQL/图表/SSE、分析调用 | 拆出任务编排、SQL 策略、分析引擎和回答组合职责 |
| `backend/apps/ai2bi/skill_router.py` | Agent 路由、Skill 与规则加载 | 路由必须接入当前用户授权和资产版本解析 |
| `backend/apps/ai2bi/evidence_builder.py` | EvidencePack 初版 | 引入指标上下文、查询集合、结果 hash、事实和版本快照 |
| `backend/apps/ai2bi/qa_checker.py` | 结果与答案检查初版 | 支持配置化硬拦截和逐事实证据校验 |
| `backend/apps/datasource/*` | 数据源、表字段、行列权限 | 成为最终执行策略的权威输入，而非仅 Prompt 上下文 |
| `frontend/src/views/chat/*` | 流式结果、SQL、图表、分析块 | 呈现 AnalysisTask、Contract、Evidence 和 QA 的明确状态 |

## 当前实现与目标的差异

当前聊天链路已可从 `/chat/question` 流式返回 SQL、数据、图表、分析与 QA 事件；AI2BI 的 Agent、资产和 Skill 管理页面也已经存在。需要明确的是：现有 Agent 表范围、隔离规则和分析规则部分仍仅作为模型上下文，不能视为最终执行策略；Evidence 目前未稳定保存完整资产版本、计算事实和完整分析结果；基础分析也尚未成为独立的确定性引擎。
