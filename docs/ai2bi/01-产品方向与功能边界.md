# 产品方向与功能边界

## 定位与目标用户

AI2BI 面向有数据分析需求、但不应直接编写 SQL 的内部业务人员和分析人员。产品目标不是替代数据开发，而是把已治理的数据资产转化为可确认、可执行、可解释和可复跑的分析任务。

首期优先服务于边界明确的业务域。每一个业务域都应由业务负责人和数据负责人共同维护指标、规则、表字段语义和测试用例。

## 首期承诺能力

### 知识问答

基于已发布 Skill、指标定义和业务规则回答“指标是什么”“某个口径如何计算”等问题。知识问答不能伪装成实时取数。

### 受控取数

支持在用户有权限的 Agent、数据源、表和字段范围内生成只读查询。结果至少展示数据来源、时间范围、过滤条件、SQL 和返回行数。

### 基础业务分析

当 SQL 结果足够时，系统应支持以下确定性分析：

- 汇总：总额、笔数、客户数、均值、最大值、最小值。
- 对比：同比、环比、绝对差额、变化率。
- 趋势：按日、周、月的变化方向、峰值、谷值和波动。
- 结构：维度占比、集中度、长尾分布。
- 排名：Top N、Bottom N、贡献度和排序变化。
- 规则型异常：阈值、均值倍数、IQR、突增、突降、缺失。

分析结论由后端计算事实支撑，LLM 只负责解释、归纳和提出下一步可验证的问题。

## 分析模式

| 模式 | 使用场景 | 系统行为 | 上线优先级 |
| --- | --- | --- | --- |
| 直接查询 | 问题、指标和范围明确 | 展示关键口径后直接执行 | P0 |
| 审慎分析 | 问题存在口径歧义，或需要业务分析 | 先澄清并确认 AnalysisContract，再执行 | P0 |
| 受控探索 | 用户希望从多个角度发现现象 | 生成受限的多查询计划，过程可取消和审计 | P2 |

审慎分析应作为默认模式。用户问题缺少时间、指标定义、客群、过滤条件或比较基准时，系统必须先追问或展示候选口径，不能静默假设。

## 最终回答合同

每个完成的数据分析回答至少包含：

1. **结论**：直接回答用户问题，数字带来源标签。
2. **基本分析**：只展示当前数据支持的趋势、排名、结构、对比或异常。
3. **数据明细**：表格和适合的图表。
4. **口径与范围**：指标、时间、客群、维度、过滤条件和数据源。
5. **SQL 与证据**：已执行 SQL、来源表、查询行数、计算公式和 QA 状态。

数字来源统一标记：

- `[SQL]`：查询结果直接返回。
- `[计算]`：后端确定性计算，必须给出公式和输入。
- `[模型推导]`：模型的估算或假设，必须明确“无 SQL 依据，需用户确认”。首期默认不用于经营结论。

## 明确不做

以下能力在相应治理、模型和验证体系建立前不对用户承诺：

- 任意数据源、任意表或任意字段的访问。
- 无来源数字、模型自行补齐缺失数据。
- 未经专项设计和证据支持的因果归因。
- 无限制的多步工具调用或无限 SQL 探索。
- 数值预测、未来经营结果预测或自动经营决策。
- 未定义生命周期、敏感数据策略和权限的任意文件分析。

## 参考产品的借鉴边界

参考 AIBI 产品体现了内部数据分析工作台的方向：SSO、会话、分析模式、资产、指标、表管理、Skill、记忆、报告和数字血统。AI2BI 可以借鉴其“先澄清再分析”和“可追溯结果”的产品思路，但不能仅复制入口或工具轨迹。

权限、资产版本、证据、QA 和执行限制必须先成为可验证的后端合同，再扩展探索、报告或预测体验。
