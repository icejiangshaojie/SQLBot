# 基础分析引擎设计

## 目标

基础分析是 AI2BI 的 P0 能力。系统不应在 SQL 返回后仅让 LLM 写一段描述，而应先由后端对查询结果执行确定性计算，再让 LLM 用业务语言解释已经验证的事实。

```text
SQL 结果
  -> EvidencePack
  -> Deterministic Analysis Engine
  -> AnalysisFacts
  -> Analysis LLM
  -> QA
  -> 最终回答
```

## 职责边界

| 组件 | 应做什么 | 不应做什么 |
| --- | --- | --- |
| Agent | 识别意图、选择分析模板、制定受控查询计划 | 自行突破资产或权限边界 |
| SQL 生成器 | 根据 Contract 与已发布资产生成 SQL | 自行决定敏感口径或权限 |
| 分析引擎 | 对结构化结果做可复现计算 | 生成业务原因或经营建议 |
| 分析 LLM | 组织结论、解释事实、说明边界、提出可验证追问 | 编造数字、补齐缺失周期、做无证据因果推断 |
| QA | 校验事实、标签、范围和规则 | 代替业务负责人定义口径 |

## 核心对象

> **Phase 0 范围**：`AnalysisContext`、`AnalysisFact`、`AnalysisResult` 已在 Phase 0 落地为临时运行合同（见 `backend/apps/ai2bi/analysis_contract.py`），仅支持单结果集。`AnalysisTask`、`AnalysisPlan`、补充查询和持久化任务容器属于 Phase 1 目标。

### AnalysisPlan

```json
{
  "intent": "monthly_overview",
  "metric_refs": ["corp_deposit.balance@1.0.0"],
  "dimensions": ["day", "customer_segment"],
  "operators": ["summary", "trend", "ranking", "concentration"],
  "queries": [
    {"query_id": "total", "purpose": "期间总额", "required": true},
    {"query_id": "daily", "purpose": "每日趋势", "required": false},
    {"query_id": "segment", "purpose": "客群结构", "required": false}
  ],
  "max_queries": 3
}
```

### AnalysisFact

每条分析事实必须可定位到 SQL 结果或其他已记录的 Fact。

```json
{
  "fact_id": "fact_top5_share",
  "category": "concentration",
  "label": "前五名客户贡献占比",
  "value": 0.243,
  "unit": "ratio",
  "source_type": "backend_calc",
  "formula": "sum(top_5.amount) / total.amount",
  "input_refs": ["fact_total_amount", "query_ranking.row[0:5].amount"],
  "query_refs": ["ranking", "total"],
  "display": "24.3%",
  "confidence": "verified"
}
```

`source_type` 只允许：

- `sql`：SQL 直接返回。
- `backend_calc`：后端可复现计算。
- `model_inferred`：模型推导。首期不得作为经营结论的唯一证据。

### AnalysisTask

AnalysisTask 是一次完整分析的持久化容器，至少关联问题、用户、工作区、Contract、Plan、已解析资产版本、执行查询、EvidencePack、Facts、最终答案和 QA。

## 支持的分析算子

| 类型 | 算子 | 输入要求 | 输出举例 |
| --- | --- | --- | --- |
| 汇总 | sum、count、avg、min、max | 数值列或已聚合结果 | 总额、日均、最大值 |
| 对比 | delta、growth_rate | 至少两个可比较周期 | 环比金额、环比率 |
| 趋势 | direction、peak、trough、volatility | 有序时间序列，至少两个点 | 上升、最高日、波动区间 |
| 结构 | share、concentration、long_tail | 维度项加总与总体 | 渠道占比、Top 5 集中度 |
| 排名 | top_n、bottom_n、rank_change | 维度和排序指标 | 客户 Top 10 |
| 异常 | threshold、mean_multiple、IQR、missing | 规则与足够样本 | 高值点、连续缺失 |

所有比率运算必须处理分母为零、NULL、货币精度、时间缺口和重复维度。遇到不满足计算前提的数据，输出“数据不足”或“无法比较”，不能用默认值掩盖问题。

## 分析选择规则

### 用户问题明确时

用户问“7 月总金额是多少”，默认只规划汇总查询。若结果本身有日粒度或用户明确要求“情况怎么样”，可追加趋势或结构查询。

### 用户问题包含分析性表达时

以下表达需要更完整的 Plan：

- “情况怎么样”“表现如何”：汇总 + 趋势，必要时排名或结构。
- “主要客户/渠道”：排名 + 集中度。
- “为什么波动”：先返回波动事实；除非有专项归因 Skill 和证据，否则不回答因果。
- “环比/同比”：若比较周期未在结果中，规划补充查询；若周期口径不明，先澄清。
- “有没有异常”：按 Agent 已发布异常规则执行，必须输出规则和阈值。

## 补充查询与澄清

Agent 可以自动规划补充查询的前提：

1. 用户意图明确，且补充查询属于已允许的分析模板。
2. 指标、时间范围、客群、币种和必需过滤均已确认。
3. 查询数量不超过 Plan 限制。
4. 所有表、字段和行权限在当前 Agent 与用户权限范围内。

遇到以下情况必须先澄清：

- “余额”可能指时点余额、日均余额或月均余额。
- “客户”可能指全部客户、活跃客户、重点客户或授权客户。
- “7 月”没有明确年份且数据存在多年度。
- 用户要求“增长原因”但没有可用的归因规则或活动数据。
- 比较基准缺失，例如“同比”没有明确自然月、累计或财年口径。

## 输出规则

分析 LLM 接收的输入应包括 EvidencePack、AnalysisFacts、Contract 和允许的输出模板。它必须遵守：

1. 每个数字带 `[SQL]`、`[计算]` 或 `[模型推导]`。
2. `[计算]` 数字引用 Fact 的公式和输入。
3. 没有 Fact 支持时，只能提出待验证假设，不能作为结论。
4. 相关性不能表述为因果关系。
5. 不输出数值预测。

## 示例

### 7 月消费总额

```text
结论：7 月成功授权消费金额为 123.46 万港币。[SQL]
基本分析：日均消费为 3.98 万港币。[计算：123.46 万 / 31]
```

### 每日趋势

```text
7 月 18 日为最高消费日，金额 8.20 万港币。[SQL]
该金额是日均消费的 2.06 倍。[计算：8.20 万 / 3.98 万]
当前结果只证明该日为高值点，不能单凭金额判断发生了何种业务活动。
```

### 客户 Top N

```text
前 5 名客户合计贡献 24.3% 的消费金额。[计算]
客户 A 排名第一，贡献 8.1%。[SQL]
```

### 环比

```text
7 月金额较 6 月增加 12.30 万港币，增长 11.2%。[计算]
```

若 6 月数据未查询，系统应请求授权执行补充查询或提示“当前结果不包含 6 月，无法计算环比”。
