# Q2/Q1/Q3 专题分析框架开发计划

## 目标

本计划承接 Phase 0 已实现的聊天内可信分析闭环，补齐评审反馈中的三个关键缺口：

1. **Q2 分析意图门控**：用户只要求取数或画图时，不产出经营结论。
2. **Q1 执行详情整合**：证据链迁入执行详情，作为结果的可追溯 tab，而不是散落在独立入口。
3. **Q3 专题分析框架**：面向“最近卡交易情况”“卡活动效果如何”等业务问题，形成知识驱动、多查询取数、表格/图表展示、数据分析 BP Agent 输出发现的完整链路。

最终形态：

```text
用户问题
  -> 意图识别：知识问答 / 直接查询 / 看图展示 / 审慎分析 / 专题分析
  -> 业务域与 Agent 路由
  -> 知识、指标、规则、SQL 模板检索
  -> AnalysisContract
  -> AnalysisPlan
  -> 受控多查询执行
  -> 表格与图表充分展示
  -> Deterministic Facts
  -> 数据分析 BP Agent 撰写发现
  -> QA 阻断或放行
  -> 执行详情：SQL、数据、证据链、QA、资产快照
```

## 设计原则

1. **先判断意图，再决定是否分析。** “展示趋势图”不是“分析趋势原因”；“是多少”不是“情况怎么样”。
2. **数据展示先于结论。** 专题分析必须先让用户看到取到了哪些数据，再让 BP Agent 基于这些数据给发现。
3. **结论只来自 Evidence 与 Facts。** BP Agent 不能直接从问题和模型记忆生成经营数字。
4. **在现有聊天页演进，不重造产品壳。** 复用 `/chat/question`、`ChatRecord`、SSE、图表、Evidence 和现有 AI2BI 管理页。
5. **Q3 是架构演进，不是脚本堆叠。** 新增领域合同与编排层，把当前 `llm.py` 中混杂的 SQL、图表、分析、证据职责逐步拆出。
6. **治理不在本轮扩权。** 本计划不放宽现有只读 SQL、表白名单和数据源访问限制；完整字段/行级授权闭环继续作为治理专项。

## 参考体验取舍

OpenAI 风格可借鉴的是“对话主入口 + 工具执行状态 + 可展开证据”的交互模式：用户仍以自然语言提出任务，系统在结果区展示当前执行到哪一步，复杂细节收进可展开区域。AIBI 方向可借鉴的是工作台化组织：聊天、资产、指标、Agent、Skill、记忆、报告和数字血统服务同一个分析任务。

本项目不复制外部页面布局。当前本地聊天页已有主入口、历史会话、SQL/图表结果、`AnalysisRunPanel` 和 `EvidenceDrawer`，应在这些组件上演进为“结果 + 执行详情 + 专题分析任务”的一体化体验。

## 总体架构

### 后端分层

```text
chat/api/chat.py
  -> chat/task/llm.py                     # 保留聊天流入口，逐步瘦身
  -> ai2bi/analysis_intent.py             # Q2：意图识别与门控
  -> ai2bi/analysis_contract.py           # 合同对象扩展
  -> ai2bi/analysis_planner.py            # Q3：专题分析计划
  -> ai2bi/analysis_orchestrator.py       # Q3：多查询编排
  -> ai2bi/analysis_engine.py             # Facts 计算
  -> ai2bi/evidence_builder.py            # Evidence Pack
  -> ai2bi/qa_checker.py                  # QA
```

`llm.py` 的目标职责是接受聊天请求、发送 SSE、协调现有 SQLBot 兼容逻辑。AI2BI 的业务分析判断、计划、证据和 QA 应逐步迁移到 `apps/ai2bi/*`。

### 前端分层

```text
ChartAnswer.vue
  -> AnalysisRunPanel.vue                 # 状态摘要
  -> ExecutionDetailsPanel.vue            # Q1：执行详情容器
     -> ResultDataTab.vue                 # 表格/样本/行数
     -> ChartTab.vue                      # 图表
     -> SqlTab.vue                        # SQL 与执行摘要
     -> EvidenceTab.vue                   # 证据链/Facts/公式
     -> QaTab.vue                         # QA findings
     -> AssetSnapshotTab.vue              # Agent/Metric/Rule/Template 快照
  -> TopicAnalysisPanel.vue               # Q3：专题分析结果组织
```

执行详情不替代主结果。主结果只放用户最需要看的内容：结论、关键表格、关键图表、状态提示。执行详情用于审计和定位。

## 意图模型

新增 `AnalysisIntent`，作为所有后续行为的前置判断。

```json
{
  "intent_type": "knowledge | data_lookup | chart_only | analysis | topic_analysis | prediction | unsupported",
  "analysis_required": false,
  "chart_required": true,
  "contract_required": false,
  "confidence": 0.86,
  "reason": "用户要求用柱状图展示趋势，但未要求解读、发现或原因分析",
  "signals": ["柱状图", "展示", "趋势"]
}
```

### 意图类型与行为

| intent_type | 示例 | 后端行为 | 前端状态 |
| --- | --- | --- | --- |
| `knowledge` | “日均余额口径是什么” | 走知识问答，不执行 SQL | 知识回答 |
| `data_lookup` | “7月消费总金额是多少” | SQL + 表格，可选图表，不分析 | 取数完成 |
| `chart_only` | “用柱状图展示7月每日消费金额趋势” | SQL + 图表，分析 `skipped` | 图表完成，分析跳过 |
| `analysis` | “7月消费情况怎么样” | 单轮分析或轻量多查询 | 分析中/完成 |
| `topic_analysis` | “最近卡活动效果如何” | Q3 专题分析计划 | 专题分析任务 |
| `prediction` | “预测下月金额” | 当前默认阻断或转待支持 | 不支持/阻断 |
| `unsupported` | 越权、跨域不明、口径不可判定 | 澄清或阻断 | 需补充信息 |

### Q2 门控规则

第一版采用规则优先、模型兜底的轻量实现：

1. 明确展示词：`画图`、`柱状图`、`折线图`、`展示`、`可视化`，且没有分析词时，判为 `chart_only`。
2. 明确取数字词：`多少`、`列出`、`查询`、`明细`、`总金额`，且没有分析词时，判为 `data_lookup`。
3. 分析词：`分析`、`情况怎么样`、`表现如何`、`发现`、`洞察`、`解读`、`异常`、`原因`、`效果`，判为 `analysis` 或 `topic_analysis`。
4. 专题词：`最近`、`活动效果`、`客户活跃`、`交易情况`、`渠道变化`、`客群表现`，结合 Agent/Skill 命中后判为 `topic_analysis`。
5. 预测词：`预测`、`预计`、`未来`、`下月会达到`，当前默认 `prediction` 并阻断数值预测。

规则结果需持久化到 Evidence，便于解释“为什么这次没有结论”。

## Q1 执行详情设计

### 目标

把证据链迁入结果的“执行详情”中，统一展示取数、图表、SQL、证据、QA 和资产快照。用户默认看到业务结果，需要追溯时再展开。

### 信息结构

```text
结果区
├── 状态摘要：意图、Agent、数据源、行数、QA
├── 主结果：结论或取数/图表结果
└── 执行详情
    ├── 数据
    ├── 图表
    ├── SQL
    ├── 证据链
    ├── QA
    └── 资产快照
```

### Tab 说明

| Tab | 内容 | 来源 |
| --- | --- | --- |
| 数据 | 返回行数、字段、样本、完整表格入口 | ChatRecord.data / Evidence.result |
| 图表 | 当前图表配置与渲染结果 | ChatRecord.chart |
| SQL | SQL 文本、表、分区、过滤、执行状态 | Evidence.sql |
| 证据链 | `sourced_numbers`、AnalysisFacts、公式、行/列引用 | Evidence.analysis_facts |
| QA | findings、summary、renderable、阻断原因 | Evidence.qa_result |
| 资产快照 | Agent、Skill、Metric、Rule、Template、route | Evidence.route_info / metric_context |

### 交互规则

1. `chart_only` 和 `data_lookup` 也显示执行详情，但 QA 只展示结果级检查，不显示分析结论 QA。
2. `blocked` 时主结果显示阻断原因，数据和 SQL 仍可在执行详情查看。
3. `skipped` 时显示“未触发分析”，并展示意图判断原因。
4. 刷新历史会话后，执行详情可通过 `GET /ai2bi/evidence/{record_id}` 懒加载。

## Q3 专题分析框架

### Q3-MVP 范围

第一版只做“单轮、有限多查询、无服务端长期任务中心”的专题分析，避免一次性引入完整任务系统。

支持两个专题模板：

1. `card_transaction_overview`：卡交易近期情况。
2. `campaign_effect_review`：卡活动效果复盘。

每个专题最多 3 条 SQL：

| query_id | 用途 | 是否必需 |
| --- | --- | --- |
| `summary` | 总览指标，如金额、笔数、客户数 | 必需 |
| `trend` | 时间趋势，如按日/周/月 | 可选 |
| `breakdown` | 结构拆解，如渠道、地区、客群、活动分组 | 可选 |

### AnalysisContract

```json
{
  "question": "最近卡活动效果如何",
  "intent_type": "topic_analysis",
  "agent_ref": "card_analysis_agent@current",
  "topic_template": "campaign_effect_review",
  "metrics": ["消费金额", "交易笔数", "活跃客户数"],
  "time_range": {"start": "2026-07-01", "end": "2026-07-31", "grain": "day"},
  "population": "授权可见客户",
  "dimensions": ["渠道", "地区", "客群"],
  "mandatory_filters": ["成功授权", "排除ATM"],
  "comparison_baseline": "活动前同期或上月",
  "status": "inferred | needs_confirmation | confirmed"
}
```

Q3-MVP 中，口径足够明确时可自动进入 `confirmed`。缺少关键口径时先返回澄清卡，不执行多查询。

### AnalysisPlan

```json
{
  "plan_id": "plan_xxx",
  "mode": "topic_analysis",
  "max_queries": 3,
  "queries": [
    {"query_id": "summary", "purpose": "获取期间汇总", "required": true, "status": "pending"},
    {"query_id": "trend", "purpose": "获取每日趋势", "required": false, "status": "pending"},
    {"query_id": "breakdown", "purpose": "获取渠道/客群结构", "required": false, "status": "pending"}
  ],
  "operators": ["summary", "trend", "ranking", "structure"],
  "limits": {"max_rows_per_query": 1000, "timeout_seconds": 60}
}
```

### 多查询 Evidence Pack

Phase 0 的 Evidence 是单 SQL。Q3 需要扩展为多查询：

```json
{
  "contract": {},
  "plan": {},
  "queries": [
    {
      "query_id": "summary",
      "sql": {},
      "result": {},
      "result_hash": "...",
      "status": "completed"
    }
  ],
  "facts": [],
  "bp_output": {},
  "qa_result": {}
}
```

历史兼容：`GET /ai2bi/evidence/{record_id}` 仍返回单记录详情；新增字段保持 nullable，旧记录没有 `contract/plan/queries` 时前端显示为空。

### 数据分析 BP Agent

BP Agent 的职责不是取数，也不是自由生成事实。它只做三件事：

1. 从 Facts 和已展示表格中归纳业务发现。
2. 标明每个发现依赖哪些 `fact_id` 或 `query_id`。
3. 对缺失数据提出下一步可验证问题。

输出合同：

```json
{
  "executive_summary": [
    {"text": "7月卡消费金额较期初呈上升", "fact_ids": ["trend_direction"]}
  ],
  "findings": [
    {"category": "trend", "text": "7月18日为峰值", "fact_ids": ["trend_peak"]},
    {"category": "structure", "text": "Top 5 渠道集中度为...", "fact_ids": ["top5_share"]}
  ],
  "limitations": ["当前结果未包含活动前基准，不能判断活动增量贡献"],
  "next_questions": ["是否补充活动前30天同口径数据？"]
}
```

前端可先渲染为 Markdown，但后端必须保存结构化 JSON，QA 也按结构化字段校验。

## SSE 与 API 合同

### 新增或扩展 SSE 事件

| type | 负载 | 用途 |
| --- | --- | --- |
| `analysis_intent` | `{intent_type, analysis_required, reason, confidence}` | Q2 意图解释 |
| `analysis_status` | `{status, message}` | 兼容 Phase 0 状态 |
| `analysis_contract` | `{contract, status}` | Q3 口径展示或澄清 |
| `analysis_plan` | `{plan}` | Q3 查询计划展示 |
| `analysis_query_status` | `{query_id, status, row_count?, message?}` | 多查询进度 |
| `analysis_dataset` | `{query_id, columns, row_count, sample}` | 表格数据摘要 |
| `evidence_qa` | `{content}` | QA 结果 |
| `analysis` | `{content}` | QA 放行后的正文 |
| `evidence_ready` | `{record_id, evidence_id, status}` | 证据可加载 |

### API 调整

1. `GET /ai2bi/evidence/{record_id}`：扩展返回 `intent`、`contract`、`plan`、`queries`、`bp_output`。
2. 可选新增 `GET /ai2bi/evidence/{record_id}/summary`：供聊天历史批量水合状态摘要。
3. 暂不新增独立任务列表 API。Q3-MVP 仍挂在 ChatRecord/Evidence 上。

- 手工验收主聊天、历史刷新、MCP 流式、MCP 非流式。

## 数据库与持久化策略

Q2/Q1 不需要新增表。优先扩展现有 `ai2bi_evidence` JSON 字段或 nullable 字段：

- `analysis_intent`：JSON。
- `analysis_contract`：JSON。
- `analysis_plan`：JSON。
- `query_results`：JSON，多查询摘要。
- `bp_output`：JSON。

Q3-MVP 仍使用 `ChatRecord + Ai2biEvidence` 承载，不新增 `AnalysisTask` 表。只有当专题分析需要任务列表、服务端取消、恢复、重跑、严格资产版本复现时，再进入独立 `AnalysisTask` 迁移。

## 验收标准

1. 纯画图请求不生成分析结论，状态为 `skipped`，执行详情能解释跳过原因。
2. 直接查询只回答直接数字或表格，不附带未经请求的经营分析。
3. 明确分析请求进入分析链路，并保留 Phase 0 的 QA 阻断能力。
4. 证据链出现在执行详情 tab 中，SQL、Facts、QA、资产快照可以同一入口查看。
5. 专题分析问题能生成 Contract 和 Plan，最多 3 条受控查询。
6. 专题分析必须先展示数据表格/图表，再展示 BP Agent 发现。
7. BP Agent 的每个经营数字都能关联到 `sql` 或 `backend_calc` Fact。
8. 缺比较基准、缺活动标识、样本不足时显示限制，不输出活动效果或因果结论。
9. MCP 流式和非流式调用都能持久化 intent、status、Evidence。
10. 现有 SQL、图表、Excel/PNG 导出、知识问答和历史会话不回归。

## 风险与控制

| 风险 | 控制 |
| --- | --- |
| 意图误判导致该分析时没分析 | 前端显示 intent 与原因；提供“继续分析”入口作为后续增强 |
| 模板过早泛化失控 | Q3-MVP 只做两个专题模板，每个模板固定数据需求和限制 |
| 多查询扩大权限风险 | 不放宽现有 SQL 白名单；每条 SQL 继续走既有只读和表策略 |
| BP Agent 编造结论 | 输入只给 Evidence/Facts；QA 校验数字和因果；block 不展示正文 |
| 前端信息过载 | 主结果保持简洁，执行详情折叠和 tab 化 |
| `llm.py` 继续膨胀 | 新逻辑进入 `apps/ai2bi/*`，`llm.py` 只做兼容入口和 SSE 转发 |

## 明确后置

以下能力不纳入 Q3-MVP：

- 完整 `AnalysisTask` 任务中心、任务列表、服务端恢复和取消。
- 字段级、行级、导出级授权闭环。
- 资产发布审批、不可变版本、严格历史重跑。
- 自由探索、自动归因、预测模型。
- 任意跨域多表分析。

这些能力应在 Q3-MVP 验证稳定后，按治理专项和 Phase 1/2 继续拆分。
