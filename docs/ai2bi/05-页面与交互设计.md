# 页面与交互设计

## 设计原则

AI2BI 使用现有 Vue 3、Element Plus 和 `Ai2biLayout` 工作台模式演进，不重做一套营销型门户。目标用户需要反复比较、确认口径、查看数据和管理知识资产，因此页面应保持信息密度、状态明确和渐进披露。

现有前端已具备聊天、资产、表管理、指标、Agent、Skill、记忆和数据开发占位页。后续重点是把它们通过统一的“分析上下文”和“资产发布治理”连接起来。

## 全局信息架构

```text
AI2BI 工作台
├── 新分析
├── 会话与专题分析
├── 报告
├── 数据资产
│   ├── 业务域
│   ├── 表与字段
│   ├── 指标
│   ├── 业务规则
│   ├── SQL 模板
│   └── 血缘
├── Agent 管理
├── Skill 开发
├── 数据开发
└── 我的记忆
```

数据源连接配置属于管理员能力，可继续复用传统 `/ds/index` 管理页；AI2BI 中展示的是“当前分析可用的数据源与权限范围”，而不是把连接配置暴露给普通业务用户。

## 页面一：聊天与 AnalysisTask 工作台

### 目标用户与入口

所有已授权分析用户从“新分析”或历史会话进入。当前聊天页可复用流式 SQL、数据、图表和分析块能力。

### 固定上下文栏

在输入区或结果区上方展示当前分析上下文，避免用户不知道系统实际会访问什么：

```text
[审慎分析]  Agent: 对公存款分析  数据源: ODPS  业务域: 对公存款
指标: 未确认  时间: 未确认  权限范围: 已应用
```

上下文栏支持查看详情，不允许普通用户直接绕过 Agent 或权限切换表。

### 输入与模式

- 模式使用分段控件：`直接查询`、`审慎分析`、`受控探索`。
- `审慎分析` 默认选中。
- 探索模式未开放时显示“暂未开放”并说明需要受控多查询权限。
- 附件入口在文件生命周期、脱敏和权限策略明确前不作为正式分析入口。

### 任务进度

替代技术日志作为默认可见信息：

```text
已识别业务域 -> 已确认口径 -> 正在查询 1/3 -> 正在计算趋势 -> 正在生成分析 -> 已完成
```

“获取表结构”“加载 Skill”“执行 SQL”等技术轨迹放入“执行详情”折叠区。用户能理解过程，但不会被底层日志淹没。

## 页面二：口径确认卡

### 触发条件

指标、时间、客群、币种、维度、过滤或比较基准有影响结果的歧义时展示。用户确认后才能进入 `contract_confirmed`。

### 卡片字段

| 字段 | 展示方式 | 是否可编辑 |
| --- | --- | --- |
| 问题理解 | 简短自然语言 | 否 |
| 指标 | 指标名称和定义摘要 | 是，受 Agent 范围限制 |
| 时间范围 | 日期或期间控件 | 是 |
| 客群/范围 | 标签或选择器 | 是 |
| 维度 | 多选标签 | 是 |
| 必需过滤 | 只读规则标签 | 否，需给出原因 |
| 分析内容 | 汇总、趋势、排名等标签 | 是，受模板限制 |
| 数据源 | 只读 | 否 |

操作包括“确认并查询”“修改口径”“取消”。用户修改后，系统重新校验 Agent、指标和权限范围。

## 页面三：分析结果区

结果按固定顺序组织，避免“SQL、图表、分析文字”散落：

1. **结论**：一至三条直接回答，数字有来源标签。
2. **基本分析**：仅渲染当前有事实支持的汇总、趋势、结构、排名或异常区块。
3. **数据明细**：表格和图表，复用现有 `ChartBlock` 与图表组件。
4. **口径与范围**：指标、时间、维度、过滤、数据更新时间。
5. **证据与执行详情**：可展开的 SQL、来源表、行数、计算公式、QA。

分析块必须显示状态：`已验证`、`数据不足`、`未执行`、`受规则限制`。不能把缺失分析块默默隐藏，导致用户误以为所有维度都已分析。

## 页面四：Evidence 与数据血统抽屉

从结果区“查看证据”打开，复用现有 Element Plus `el-drawer` 与描述列表模式。

| Tab | 内容 |
| --- | --- |
| 分析契约 | 指标、时间、客群、维度、过滤、确认记录 |
| 查询 | 每条 SQL 的用途、执行状态、行数、表和字段 |
| 数字来源 | `[SQL]`、`[计算]`、`[模型推导]` 及公式和引用 |
| 数据血统 | 表级血缘、来源数据源、刷新时间；后续支持字段级血缘 |
| QA | 通过、警告、阻断原因和处理建议 |
| 资产版本 | Agent、Skill、Metric、Rule、Template 的解析版本 |

仅显示当前用户有权查看的证据。下载、复制 SQL、导出结果均应二次检查权限和脱敏策略。

## 页面五：报告详情与重跑

报告不是仅保存一段 Markdown。报告详情应绑定完整 AnalysisTask，提供：

- 问题和 AnalysisContract。
- 最终回答、图表和数据摘要。
- Evidence、资产版本和 QA。
- “按原口径重跑”“复制为新分析”操作。

“重跑”默认使用当前已发布资产重新生成 AnalysisPlan，并在界面提示原报告版本与当前版本是否不同。需要严格复现时，使用报告保存的资产版本和权限允许的历史数据快照。

## 页面六：数据资产

复用现有“业务域左侧树 + 右侧 Tab + 详情抽屉”的模式，扩展为统一资产入口。

| Tab | 核心内容 | 主要操作 |
| --- | --- | --- |
| 业务域 | 边界、负责人、状态、关联 Agent | 查看、申请维护、创建草稿 |
| 表与字段 | 物理对象、语义、敏感性、更新频率 | 查看映射、申请编辑 |
| 指标 | 定义、公式、粒度、时间口径、状态 | 搜索、对比版本、创建草稿 |
| 规则 | 适用范围、正反例、严重度 | 查看、提交修订 |
| SQL 模板 | 场景、参数、依赖资产、测试状态 | 预览、测试、创建草稿 |
| 血缘 | 来源、目标、关系和版本 | 查看影响范围 |

资产浏览可面向普通用户开放已发布版本；草稿、审核、发布和删除仅对对应角色开放。

## 页面七：表与字段管理

现有表管理页适合作为物理与语义映射管理入口。需要明确区分：

- 执行状态：是否在数据源白名单、是否可被 Agent 使用。
- 业务状态：是否有中文含义、字段角色、敏感级别、质量要求。
- 权限状态：当前用户是否可查看、查询、导出。

避免当前“数据源名称与 ID 写死”的表现，页面必须从当前工作区配置和 API 返回中获取数据源列表。

## 页面八：指标管理

指标页应从普通 CRUD 变为生命周期管理：

```text
草稿 -> 审核中 -> 已发布 -> 已弃用 -> 已归档
```

详情包含定义、公式、允许维度、强制过滤、来源表字段、样例 SQL、测试状态、依赖关系和版本记录。删除已发布指标应替换为弃用，保留历史任务引用。

## 页面九：Agent 管理

每张 Agent 卡片/详情明确展示：业务域、能力范围、路由信号、可用指标、表策略、Skill、分析模板、QA 策略、测试结果、版本和发布状态。

发布按钮必须提示影响范围，并在后续实现中由测试门禁控制。Agent 授权与权限申请应在此页管理，但普通用户不应看到或编辑其他人的授权信息。

## 页面十：Skill 开发与测试

现有文件树、编辑、预览和测试对话可保留，新增：

- 结构化 Front Matter 表单或校验提示。
- 引用资产选择与有效性校验。
- 指定 Skill 测试与生产路由测试切换。
- 路由、SQL、Evidence 测试结果。
- 草稿、审核、发布和版本比较。

Skill 测试不能固定数据源 ID，应继承所选 Agent/工作区的分析上下文。

## 页面十一：数据开发

现有页面是占位，应先纳入左侧导航并明确职责：维护已验证 SQL 模板、查看查询计划和运行记录、配置测试数据，不是面向普通业务用户的自由 SQL IDE。

## 页面十二：我的记忆

个人记忆页展示记忆内容、类别、来源、范围、置信度、置顶和到期时间。用户可修改、删除和禁用个人记忆；团队/全局记忆应走资产审核流程，不能通过个人记忆页直接写入。

## 现有前端演进约束

- 统一 `Ai2biLayout.vue` 与遗留 `Menu.vue` 的导航来源，避免两份菜单漂移。
- 提炼重复的页头、统计条、域筛选、详情抽屉和资产状态组件。
- AI2BI 新页面遵循现有浅灰工作区、白色内容面板、绿色主色和 6-8px 圆角，不设计嵌套卡片。
- 桌面工作台优先，但核心输入、结果和抽屉必须具备窄屏可读布局。
- 所有硬编码的数据源、业务域和默认 ID 改为由工作区上下文和后端配置提供。
